# The intermediate data model

> 日本語: [DATA_MODEL.ja.md](DATA_MODEL.ja.md)

This document defines `ESP32KeyBridge`'s intermediate data representation. Input adapters, the transformation pipeline, and output adapters connect to each other through nothing but the representation defined here.

Per-use-case validation records are in [USE_CASES.ja.md](USE_CASES.ja.md); the reasoning and status of each decision is in [DECISIONS.ja.md](DECISIONS.ja.md).

## Design principles

1. **The bridge does not interpret.** Deciding what character a key means is, as a rule, the host's job (the PC's OS). The bridge carries key identifiers and interprets only where it must (layout conversion, typing text).
2. **State is owned by whoever interprets it.** The bridge never owns the authoritative copy of information it does not interpret (lock state is the applied case of this principle).
3. **The core holds no clock.** It never reads the time, and time-dependent work (debouncing, pacing, timeouts) stays inside adapters.

## Key identity: kind + code

A key or button's identity is the pair **(kind, code)**. Each kind has its own independent code space.

| Kind | What the code means | Examples |
|------|---------|-----|
| keyboard | numerically identical to the HID keyboard page (0x07) Usage ID | A=0x04, Enter=0x28, LeftCtrl=0xE0, CapsLock=0x39 |
| consumer | numerically identical to the HID consumer page (0x0C) Usage ID | Volume Up=0x00E9, Mute=0x00E2, Play/Pause=0x00CD |
| mouse_button | button number | left=1, right=2, middle=3, ... |
| virtual | bridge-internal only (layer triggers, macro triggers, mode toggles) | numbered freely. **Never reaches an output adapter** |
| ~~Future extensions~~ | ~~System Control, absolute coordinates, ...~~ | Out of scope |

- A keyboard code is a **layout-independent physical key identifier**. A JIS keyboard and a US keyboard both send 0x04 for the key where A sits; interpreting the engraving is the host's job.
- Keeping HID-derived kinds numerically identical to their usages means pass-through and remapping **need no conversion table at all**.
- Whether the representation is a struct pair or a partitioned integer is an implementation choice. The only thing fixed as specification is that identity is kind + code.

## The two classes of traffic

Everything flowing through the intermediate representation falls into one of two classes. When adding a new input or output, determining this class first makes the processing rules follow mechanically.

| | Held (state) | One-shot (event) |
|---|---|---|
| Meaning | means something while held | the moment it happens is all there is; consumed once |
| Representation | pressed set (a snapshot) | an ordered queue |
| Merging | union | joined in arrival order |
| On disconnect | cleared and fully released | pending items discarded |
| Repeat | generated by the host from the state | no such concept |
| Examples | keyboard keys, modifiers, consumer keys, mouse buttons | characters, key action sequences (macros), mouse movement and wheel |

- **Consumer keys are held state.** Whether a host reacts on the edge (Play/Pause) or continuously while held (volume) is the host's interpretation, and the bridge takes no position — the same attitude it takes toward the difference between keyboard Enter and CapsLock.
- **For a mouse, buttons are held state; movement and wheel are one-shot (relative deltas).**
- Lock state is "held state travelling the other way" (host -> bridge -> inputs); see below.

## Rules for held state

### The pressed set

- Each input holds its own pressed set, and merging is their **union**. A key's release becomes effective **when every input has let go of it**.
- Modifiers (0xE0-0xE7) enter the pressed set under the same rules as ordinary keys. The difference between the HID report's modifier bits and its key array bytes is normalized away by the input adapter and re-split by the output adapter when it builds a report.
- The pressed set holds **logical presses**. A one-to-one correspondence with physical state is not required: toggles (each stomp alternately issues Shift press and release), one-shots, and encoder pulses (synthesized taps) are all expressed by the adapter synthesizing logical presses.
- **When an input disconnects or disappears, its pressed set is cleared and reflected into the merge as a full release** (stuck-key prevention). Detecting the disconnect is the adapter's job; clearing and reflecting it is the core's.

### Remapping

- A remap is **a single-step lookup and never chains**. Two entries, `CapsLock->LeftCtrl` and `LeftCtrl->CapsLock`, constitute a swap.
- Remaps **cross kinds** (keyboard F13 to volume up, a mouse side button to a keyboard key, any key to a virtual key).
- Disabling a key (dropping it) uses the same mechanism.

### Layers

- A physical Fn key never appears on HID, so it can be neither observed, shared, nor remapped (a limit in principle). The equivalent is built by remapping a key that *does* reach HID into a virtual key, consuming it, and enabling a layer (an overlay substitution table) while it is held. A keyboard you built yourself can emit virtual keys directly from its adapter's assignment.
- **The substitution is fixed at press time, and a release releases what was resolved then** (the rule that must hold, so that releasing after a layer is dismissed cannot create a stuck key).
- Layer state is managed after merging and by default **applies to every input** (the basis for split keyboards and foot-pedal Fn).
- ~~Tap/hold (tap for the original key, hold for Fn)~~ is out of scope.

## Rules for one-shot events

There are three one-shot payloads, and the rules (order preserved, joined in arrival order, queued) are common to all of them.

### The text stream

A one-way sequence of Unicode characters expressing "type this string, in this order".

Sources:

- Text macros (produced in exchange for consuming a virtual key trigger)
- External commands (a string received over serial or the network)
- Text devices (a serial-attached barcode reader, and so on)

Rules:

- A string is **carried as characters all the way to the output edge**, where the output's keyboard layout description expands it into keystrokes (so that macro definitions stay independent of the output's layout).
- Remaps and layers do not apply to the text stream (they are for keys).
- **Escapes are not interpreted.** Interpreting `"\n"` belongs to whoever builds the string (a compiler or a parser); the bridge only ever sees actual control characters.

Which characters are accepted (input takes any code point as UTF-8; whether it can be typed is decided next):

| Class | Behaviour |
|---|---|
| A printable character present in the host layout table | typed (Shift synthesized as needed, Caps Lock compensated from the internal shadow, digits on the main row rather than the keypad) |
| The five control characters (table below) | the corresponding key is pressed |
| Anything else (kana, kanji, emoji, symbols absent from the table, other control characters) | dropped and counted (`textEncodeFailCount`) |

Printable coverage per preset:

| Preset | Printable characters that can be typed |
|---|---|
| `en_us` | ASCII printables (U+0020-U+007E) |
| `ja_jp` | ASCII printables (U+0020-U+007E) plus `¥` (U+00A5) |
| Generated locales (below) | the printables of each layout's base / Shift / AltGr / AltGr+Shift planes (including locale-specific `ä ö ü ß € £ ñ ő`) |

`en_us` and `ja_jp` are hand-written. The rest are generated from the shared 4-plane tables (`EspUsbHost/src/keymap/*.h`) into `KeyboardLayoutEntry[]` by `tools/gen_keymaps.py`, emitted to `src/ESP32KeyBridgeLayouts.inc`. The 14 generated locales are **`de_de` / `fr_fr` / `es_es` / `it_it` / `nl_nl` / `da_dk` / `nb_no` / `sv_se` / `fi_fi` / `en_gb` / `pt_pt` / `pt_br` / `fr_ch` / `hu_hu`**. Fetch them with `KeyboardLayout::byName("fr_fr")` and friends (`de_de` also has `deDe()`).

Generation rules:

- The columns are the base / Shift / AltGr / AltGr+Shift Unicode code points (0 = no character on that plane).
- `capsAffects` is derived from "the Shift column equals the Unicode uppercase of base" (per the memo). Latin-1's `ä -> Ä` and Latin Extended-A's `ő -> Ő` / `ű -> Ű` are judged correctly through Unicode uppercasing.
- Control keys (Enter / Tab / Esc / Backspace) and the keypad are excluded from the table (the former belong to the typing engine, the latter expand onto the main row by policy).
- A single source keeps four projects in sync, and fixes to the shared tables arrive by regeneration.

Every consumed character, including the dropped ones, still reaches text-capable outputs (`writeText`); only HID output is constrained by what can be typed.

Standard control character assignments:

| Character | Keystroke |
|---|---|
| 0x09 (TAB) | Tab |
| 0x0A (LF) | Enter |
| 0x0D (CR) | Enter (a following LF is dropped, so CRLF is one Enter) |
| 0x08 (BS) | Backspace |
| 0x1B (ESC) | Escape |
| other control characters | dropped and counted |

### Key action sequences

**An ordered sequence of synthesized keystroke instructions (down / up / delay).** A user's real key presses are always held state and never travel through this sequence.

Sources:

- Key sequence macros (Ctrl+C, Alt+Tab, Ctrl+V, with delays in between)
- The expansion of the text stream (joining at the output edge)
- Synthesized taps (those in contexts that require ordering guarantees)

Rules:

- Instructions **act on the output pressed set in order** as they are consumed (this is the junction between one-shot and held).
- **The frame of one character (Shift down, key down/up, Shift up) is atomic** and nothing else interleaves.
- Coexistence with modifiers the user is holding works by parking, typing, and restoring per character. An option to "defer consumption until modifiers are released" exists (default: immediate, in arrival order).
- Pacing (report interval, inter-character delay) belongs to the adapter. The queue is fixed-capacity and its free space can be queried (backpressure). Feeding a string **stops rather than drops** once the queue is full and returns the amount consumed, so the caller can resume from there. Only the paths that cannot resume (inside a macro, single-character injection) drop on overflow and count it.
- Implementation note: modifier changes and keystrokes are sent as separate reports (a guard against ordering ambiguity within a single report).

### Relative deltas

Events of `(axis, delta)`. The axes are X / Y / wheel / horizontal wheel (mouse-side).

- **Additive**: consecutive events on the same axis can be compressed by summing (unlike characters, a congested queue can shrink them instead of dropping them).
- Outputs sum them per report interval and carry whatever exceeds the report's range into the next one.
- Per-axis **inversion and integer scaling** are core transforms (natural scrolling and the like). Curved transforms such as pointer acceleration are out of scope.

## Lock state and LEDs

### The authority rule

- Locks are interpreted by the host. **While a lock-reporting output (USB device / BLE HID) exists, that output is the authority.** The bridge only relays and never toggles by itself.
- **The authority is the active lock-reporting output, and there is always exactly one.** Since v1 has no output-switching feature, it is fixed to the first registered lock-reporting output. If several are registered, drift between the hosts' lock states is not tracked (not forbidden, not reconciled either). One lock-reporting output is the recommendation.
- **While no authority exists (USB unplugged, or the outputs are UART only), the bridge is the terminal host**, owns the authoritative copy, and toggles its internal state on a lock key press (Caps Lock / Num Lock / Scroll Lock; kana is excluded). When an external authority appears, its first report overwrites (external wins); when it disappears, the bridge carries on from the last value.

### The internal shadow and notification

- The bridge always keeps exactly one internal LockState (all off at startup). It is overwritten by reports from the authority, and **every input adapter is notified** when it changes.
- How that notification is realized is up to the adapter (an LED report to a USB keyboard, pin outputs to a homemade GPIO keyboard, an output report over BLE).
- An input that connects later is notified with the state as of that moment (a host only sends a report on change, so holding it internally is mandatory).
- ~~Active lock synchronization (injecting toggle keys into a host that has drifted)~~ is out of scope.

## Keyboard layout conversion

For setups where the keyboard's engraved layout differs from the host OS's layout setting (for example, a US-engraved keyboard on a Japanese Windows). Opted into per input.

### The structure of the conversion

- What is needed is a **(key, shift) -> (key, shift)** table. Substituting the usage alone cannot express symbols on the Shift plane (US Shift+2 = `@` is 0x2F unshifted on ja_jp).
- **Identity keys pass straight through** — letters, digits (unshifted), navigation, modifiers, and so on. Only symbols convert (about 15 keys between US and JA).
- **Shift suppression and synthesis**: drop it on output even when physically held; press it on output even when not. It is maintained while held (preserving long presses and auto-repeat).
- Keys absent from the physical keyboard can still be sent (`_` = Shift+0x87, and so on). Supplying IME keys such as Henkan / Muhenkan / Kana is done with **ordinary remaps**, not with the conversion table.
- Whether the table is derived from a keyboard layout description (character <-> (key, Shift/AltGr)) or held as pairs directly is an implementation choice. Presets are named in locale form (`en_us`, `ja_jp`, `de_de`).
- **All four planes (base / Shift / AltGr / AltGr+Shift) are supported.** `KeyboardLayoutEntry` carries `altGr` / `altGrShift` code point planes and `KeyStroke` carries a Right Alt (AltGr) flag. `encode` searches base, then Shift, then AltGr, then AltGr+Shift, and raises the flags (shift / altGr) of the plane that matched. `decode(key, shift, altGr)` consults the AltGr planes too. On an input whose engraving is a layout with AltGr planes (`de_de`, for example), Right Alt is consumed as AltGr (like Shift) and re-synthesized per converted key on the output side. On layouts without AltGr planes (`en_us` / `ja_jp`), Right Alt passes through as an ordinary shortcut modifier.

### Operational requirements and constraints

- **A way to switch conversion on and off (a hotkey or external control) is a required feature.** Conversion produces output that assumes the host interprets it with a particular layout, so in BIOS / UEFI / recovery environments, which interpret differently, it garbles instead.
- Keys pressed within a modifier combination (Ctrl / Alt / GUI held) are not converted by default and pass straight through (positional shortcuts take priority; a setting switches to converting). Letter shortcuts are identity mappings and unharmed either way.
- Simultaneously holding keys with conflicting Shift requirements (`@` and `"` at once) cannot be represented and is documented as unsupported.
- Mixed layouts across several keyboards work through per-input conversion (before merging) plus union merging. Plugging each keyboard into the PC individually cannot solve this in principle (the OS layout is single, and OS modifiers are global). The only remaining interference is the instant a converted key from one keyboard arrives while a modifier on another is held, mitigated by serialization and the deferral option.
- Machine typists (HID barcode readers and the like) are covered by the same table and are the best case: shortcut and simultaneous-press constraints effectively never arise.
- The two directions differ in practical value: US engraving to a ja_jp host covers ASCII 100%; ja_jp engraving to an en_us host cannot type `¥` and leaves gaps in coverage.

### Relationship to typing text

Expanding the text stream (character to keystroke) uses the same keyboard layout description. Digits expand onto the main row rather than the keypad (independent of Num Lock), and letters consult the internal Caps Lock shadow to correct Shift. Characters absent from the table (kana, kanji, symbols missing from the target layout) are dropped and counted.

## Output rules

- An output adapter **emits only what it can represent and silently drops the rest**. Mouse reports appear only when a mouse-capable output is registered (the USB Device output is always composite, hence always mouse-capable); log-style outputs can also emit virtual keys and characters.
- Virtual keys are meant to be consumed inside the pipeline and do not reach output adapters (log-style diagnostic output excepted).
- Outputs are **state-snapshot based** (the same idea as a USB HID report). The boot keyboard's 6KRO limit is a constraint of the output adapter and does not reach the intermediate pressed set.
- **The text stream (`writeText`) has two sources**: characters from `typeText()` / `typeChar()` / macros, and characters from presses on inputs configured with `convertLayout()` (decoded through the engraving, one character per press edge, Enter to newline and Tab to tab). Text-capable outputs (a text UART, a log) receive these; HID outputs ignore them. This is what makes it possible to extract "presses from a HID keyboard or barcode reader" as text, with the layout decided in exactly one place: the input's convertLayout.
- The USB device composition is fixed by the descriptor at enumeration time (the USB Device output is always the keyboard + consumer + mouse composite; unused interfaces merely never send a report, which is harmless). Changing the composition at run time requires reconnecting.

## Impossible in principle (things the specification will not solve)

| # | Item |
|---|---|
| 1 | **Characters that cannot be typed**: a character absent from the target layout cannot be generated over HID (`¥` to an en_us host, and so on) |
| 2 | **Telling shortcut semantics apart**: whether an application's key binding is character-based or position-based is not observable from the bridge. Layout conversion leaves broken cases whichever way it leans |
| 3 | **The host has one modifier state**: simultaneously holding keys with conflicting Shift requirements cannot be represented. Keystroke sequences and user-held modifiers are mutually exclusive in time |
| 4 | **Invisible host state**: IME on/off and the focused application are not observable. Text features assume the IME is off (IME garbling cannot be solved in the bridge; only mitigations such as an optional prefix key exist) |
| 5 | **The physical Fn key**: processed inside the keyboard and never present on HID, so it can be neither observed, remapped, nor shared |
